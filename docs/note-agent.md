## 📄 根 README 的写法 260822

**格式分工**

```text
整理时误把 note 标题规范套到 README
        │
        ├─▶ [✖] 否决：README 与 note 格式不同，要从整个文档逻辑理解
        │
        └─▶ [✅] 两套标题规范
               ├─▶ README：最多三级（### 可用）、## 不带时间信息、最终态
               └─▶ note-*：O/KR 两级（# 领域 / ## 里程碑+日期）、演化图、过程史
```

**关键认知**：两套标题规范不能混用——整理 README 时套用 note 的标题规则会被否决，需按各自格式写。

**极简范式**

```text
"关键配置速查"表与模型表（对外名）重复
        │
        ├─▶ [✖] 冗余：同一事实多处拷贝，维护必然不同步
        │
        └─▶ [✅] 根 README 极简范式：两级标题，每节只放三种数据
               ├─▶ 图（流程导航，标注命令编号）
               ├─▶ 表（决策依据，回答"选谁"）
               └─▶ 命令（可执行，按编号分段）
```

**关键认知**：判据是"同一事实只在一处出现"——实例：速查表与模型表（对外名）重复，被用户删除。

**图怎么画**

```text
根 README 的图要和下面的命令是对应关系——启动前准备什么、是否满足
        │
        ├─▶ [✖] 静态拓扑图：表达组件关系，内容是操作流程，形式没匹配内容
        ├─▶ [✖] 门控流程：仍不贴合，直接贴出岔路口样式作标准
        │
        └─▶ [✅] 岔路口样式（├─▶ 分支 / ✖ 否决 / └─▶ 采纳）
```

**关键认知**：图的形式必须匹配表达内容——拓扑图（组件关系）画不了操作流程；流程判据（门）即"启动前准备什么、是否满足"，`✖` 分支指向补救命令、`✔` 分支继续。图/命令/表协同：图标编号、命令按编号、表回答"选谁"。

## 📐 文档按照使用角色进行划分 260822

```text
模块 README 写法：每个子模块都写 README 还是统一起来
        │
        ├─▶ [✖] 统一写在根 README
        │        同一内容两处维护必然不同步（vllm README 迁移后残留旧路径）
        │
        └─▶ [✅] 分层：根 README 只做导航，详情下沉各子模块 README
               │
               ▼
            角色划分
              ├─▶ 过程文档 note-*        = 为什么这么定（历史）
              └─▶ 最终状态 README/AGENTS = 当前生效、可直接执行
                     │
                     ▼
                 视角：README → user 怎么用
                      AGENTS → AI 按什么规矩归档
                     │
                     ▼
                 处理链：[面向业务] note-* → 模块 README → 根 README
                        [面向 AI]   note-agent → AGENTS.md
```

处理链顺序固定、不可跳步——业务侧先追加 note-*、再更新模块 README、最后根 README 指路；AI 侧先 note-agent、再 AGENTS.md。

## 🎨 按对话逻辑选用多样式 ASCII 演化图 260822

> 归档时只用了最基础的单线 `|`/`v` 样式，被指出"太单一"。约定至少 3 种样式，按对话结构选用：

1. **岔路口样式**：对话中探讨了多种方案/出现认知分歧时用。`├─▶ [分支]` 列出探索分支，`✖ 否决` 标注被推翻的选项，`└─▶ [采纳]` 指向最终选择——最能还原"多个选项试错才拍板"的探索感。
2. **时间线框式**：演进步骤清晰、每步有强痛点驱动时用。`┌─┐` 框住每个阶段事件，侧边 `[顾虑爆点]` 标注卡点。
3. **对话气泡式**：内容以"快问快答/打磨细节"为主时用。左列演化轨、右列用户原话一一对应。

**选择逻辑**：方案对比/分歧 → 样式 1；痛点驱动的时间线 → 样式 2；一问一答 → 样式 3。默认优先样式 1。

## 🧭 通过 ASCII 图描述演化过程 260820

**ASCII 流程图可以很好还原对话轨迹**

**内容如何还原：**

- 演化链上的每一环，都要能在对话里找到用户原话或明确意图作证据
- 找证据按**时间顺序回看整段对话**，不是只回看最近几条
- 无法从对话中找到依据的环节，就是 AI 脑补，删掉重写
- 用户没明说但驱动决策的动机，要从后续发言反推确认，而不是猜

## ✍️ `>` 记录演化过程，而非结论 260820

> 归档时 AI 习惯写"结论式"引言（最终做了什么/不要做什么）。要的不是结论，是用户起心动念的分析和演化；且不能陷入具体案例，要有抽象。

**为什么结论式不对：**

- **结论绑定场景**：结论是"这一次"的答案，换一个用户、换一种资源、换一套约束就用不上，归档即失效
- **起心动念可迁移**：它包含问题的起源、意图的转变、真实顾虑——这些不依赖具体场景，才是未来决策能复用的部分
- **归档的读者是"未来的决策者"**：他要的不是答案本身，是"当时为什么这样想"的思维路径。结论让他少踩一次坑，起心动念让他能自己走对路

**怎么写（抽象规则）：**

1. **从"问题从何而起"写起**：最初的现象或模糊念头，不预设答案
2. **写"意图的演化"**：问题如何被重新定义，转折点在哪、为什么转向
3. **写"真实顾虑"**：那些驱动提问、但用户没明说的担忧（往往藏在问题背后）
4. **落点（方案）是演化的终点**：放最后，不前置、不先行下结论

**检验标准：** 读完 `>` 段，读者能还原"当时是怎么想的"，而不是只看到"最后做了什么"。

## 🎯 OKR 式框架 260819

> 发现 AI 整理出的二级标题太冗长，对话中一些关键的图表在归档时被删除。

**对比表保留维度的深层原因：**

候选方案对比的价值不在"谁赢"，而在于**对比维度本身**——那些维度是逐步提炼出的真需求。

**时间线两种读法：**

- 正向时间线：适合维护者回顾（跟着对话走）
- 时间倒序：适合快速看最新（面向使用者）

## 🤝 基于文档的人机协作 260816

> AI 协作中，大量设计决策与踩坑过程都来自对话，如果不归档，这些知识随会话消失，下次重复踩坑。

**设计初衷：**

- **"写入顶部 + 时间倒序"**：快速看到最新结论，不用翻到文件尾
- **"不改原内容只追加"**：保证历史不可变，便于追溯
