## ✍️ `>` 记录演化过程，而非结论 260820

> 归档时 AI 习惯写"结论式"引言（最终做了什么/不要做什么）。要的不是结论，是用户起心动念的分析和演化；且不能陷入具体案例，要有抽象。

**为什么结论式不对：**

- **结论绑定场景**：结论是"这一次"的答案，换一个用户、换一种资源、换一套约束就用不上，归档即失效
- **起心动念可迁移**：它包含问题的起源、意图的转变、真实顾虑——这些不依赖具体场景，才是未来决策能复用的部分
- **归档的读者是"未来的决策者"**：他要的不是答案本身，是"当时为什么这样想"的思维路径。结论让他少踩一次坑，起心动念让他能自己走对路

**怎么写（抽象规则）：**

1. **从"问题从何而起"写起**：最初的现象或模糊念头，不预设答案
2. **写"意图的演化"**：问题如何被重新定义，转折点在哪、为什么转向
3. **写"真实顾虑"**：那些驱动提问、但用户没明说的担忧（往往藏在问题背后）
4. **落点（方案）是演化的终点**：放最后，不前置、不先行下结论

**检验标准：** 读完 `>` 段，读者能还原"当时是怎么想的"，而不是只看到"最后做了什么"。

## 🎯 OKR 式框架 260819

> 发现 AI 整理出的二级标题太冗长，对话中一些关键的图表在归档时被删除。

**对比表保留维度的深层原因：**

候选方案对比的价值不在"谁赢"，而在于**对比维度本身**——那些维度是逐步提炼出的真需求。

**时间线两种读法：**

- 正向时间线：适合维护者回顾（跟着对话走）
- 时间倒序：适合快速看最新（面向使用者）

## 🤝 基于文档的人机协作 260816

> AI 协作中，大量设计决策与踩坑过程都来自对话，如果不归档，这些知识随会话消失，下次重复踩坑。

**设计初衷：**

- **"写入顶部 + 时间倒序"**：快速看到最新结论，不用翻到文件尾
- **"不改原内容只追加"**：保证历史不可变，便于追溯
