# Token hub

## 模型渠道接入 260831

资源池方案定完，接着要把两类资源接成渠道——本地 vLLM 与 NVIDIA 免费额度，让团队只认网关一个入口。

```text
              客户端（令牌 sk-xxx）
                      │
                      ▼
          new-api :18080（统一认证 / 额度 / 审计）
                │                        │
                ▼                        ▼
      ① 本地渠道                  ② 免费额度渠道
      127.0.0.1:18000             integrate.api.nvidia.com
      qwen3.6-35b                 openai/gpt-oss-20b
                │                        │
                ▼                        ▼
      约束在自身暴露面            约束全在上游
      └ 须绑回环防绕过            ├ key 与模型绑定
                                  ├ 模型 ID 带前缀
                                  └ 免费层排队
```

**诊断总则：先分辨是谁在报错**（两类渠道通用）

```text
客户端 ──▶ new-api :18080 ──▶ 下游（vLLM / NVIDIA）
              │                      │
              │                      ├─ {"detail":"Not Found"}         FastAPI · 路径错
              │                      ├─ The model 'x' does not exist.  OpenAI · 模型名错
              │                      └─ 404 page not found             Go · 上游自返
              │
              └─ 转述后抛出，各层差异混同 → 无从分辨
```

网关会把下游错误转述成统一格式，原有差异在转述中丢失，于是「四次 404 表象一致」——实则分属不同层级。要拆开只能靠**响应体格式**：`{"detail":"Not Found"}` 是 FastAPI 风格（vLLM 即 FastAPI），`404 page not found` 是 Go 标准库默认响应，**两者不是同一个服务在报错**。

这是两个互补手段——**看响应体**判「谁在报错」，**看下游日志**判「请求长什么样」。

**根因分析**

```text
渠道「测试」→ 404
     │
     ├─▶ ① 模型名填 qwen ──────▶ vLLM 收到 POST /v1/chat/completions
     │                             路径对，模型名不符
     │
     ├─▶ ② Base URL 带 /v1 ─────▶ 收到 POST /v1/v1/chat/completions
     │                             /v1 重复
     │
     ├─▶ ③ Base URL 去掉 /v1 ───▶ 收到 POST /chat/completions
     │                             缺 /v1
     │
     └─▶ ④ test_model 留空 ─────▶ 收到 POST /v1
                                   路径不完整
```

① 模型名由 vLLM 的 `--served-model-name` 决定，手打简写对不上，路径正确照样 404。② 网关会自动补 `/v1`，页面「不应以 `/v1` 结尾」的警告在此版本属实，重复填则拼出 `/v1/v1`。③ 是前提性错误——渠道 `type` 选成 Custom 而非 OpenAI 时拼接行为不同，Base URL 怎么改都缺 `/v1`，此前对 `/v1` 加减的所有尝试都是在错误前提下空转。④ 数据库直插渠道时 `test_model` 默认为空，测试请求退化成 POST 到 Base URL 本身。

整轮的突破口是把「网关说了什么」换成「下游收到了什么」——vLLM 的访问日志会打印真实请求路径（`docker logs | grep '"POST'`），这个手段比读网关报错可靠得多。

---

**本地渠道：必须绑回环**

渠道调通后又冒出新需求——「所有调用必须经过网关认证」。但**网关自身做不到这件事**：new-api 只管流经它的流量（无令牌返回 401，已生效），挡不住别人绕过它直连后端。

```text
团队用户 ──令牌──▶ new-api:18080 ──▶ vLLM:18000     ✔ 有认证
                                        ▲
                                        │
   任何人 ────────无认证直连─────────────┘            ✘ 绕过
```

**做法**：收窄后端暴露面，把 vLLM 端口映射由 `18000:8000` 改为 `127.0.0.1:18000:8000`，外部 IP 直连即被拒。网关侧再按人头分令牌、配额、模型白名单——网络层收窄后这些管控才有意义。

**取舍**：vLLM 自带的 `--api-key` 是应用层加固，能防本机其他账号/容器直连，但因为是单一共享密钥、无法按人区分，在「网关已负责按人管控」的分工下属于重复且更弱的一层，本轮未上；待本机会有其他人的账号或容器时再叠加。

改动落在 compose 的 `x-vllm-common` 锚点（各 profile 共用，切模型不失效），同步改两处：new-api 渠道 Base URL 与 Open WebUI 的 `OPENAI_API_BASE_URLS` 均须为 `127.0.0.1:18000`。Open WebUI 是 host 网络，本就走回环，未受影响。

**免费额度渠道：key、模型与响应**

NVIDIA 这边报的是 `404 page not found`（Go 风格），看似网络不通；实测发现 TLS 证书是 NVIDIA 真实签发、建连仅 0.002s，流量正常到达上游——404 是 NVIDIA 自己返的，**不是网络问题**。真正的坑集中在三处。

**① key 必须与模型绑定**

在账号设置页（`build.nvidia.com/settings/api-keys`）生成的 key 能 `GET /v1/models` 列出全部 83 个模型，但调任何一个都返回 403 `Authorization failed` 或 404 `Not found for account`——**目录可见不等于有权调用**。

```text
账号设置页生成 ──▶ 能列目录，调不动任何模型      ✘
        │
        └─▶ 进具体模型页（如 /openai/gpt-oss-20b）
                  │
                  ▼
            点生成 key ──▶ 与该模型绑定，可调用    ✔
```

换模型要重新生成 key；多模型可在渠道里走「多 Key 模式」轮询。官方 Getting Started 第 1 步要求先创建并验证账号才解锁完整访问，未验证是 403 的常见成因。

**② 模型 ID 必须带组织前缀**

模型页显示的 `GPT-OSS-20B` 不是 API 里的 ID，实际 ID 为 `openai/gpt-oss-20b`（组织/模型名 形式）。填无前缀的简写会 404。可用 ID 以 `GET /v1/models` 返回的为准，但那是全平台目录，能否调用取决于 key 是否绑定该模型。

**③ 响应慢的两个成因**

一是**大模型在免费层排队严重**，与配置无关：


| 模型                  | 生成 token | 耗时   | 速度        |
| --------------------- | ---------- | ------ | ----------- |
| `openai/gpt-oss-120b` | 60         | 117.8s | 0.5 token/s |
| `openai/gpt-oss-20b`  | 164        | 5.5s   | 30 token/s  |

建连 0.002s、首字节 0.6s，网络层健康，瓶颈在服务端推理排队。同系列 20B 比 120B 快约 60 倍。

二是**推理模型的思维链长度随机**。同一句 Say hello，completion token 在 17~249 间波动——模型有时想一句就答，有时反复推演。

```text
同一请求，三次调用
   ├─ 默认                    → 249 token（大段思维链）→ 慢
   ├─ 默认                    → 65 token              → 3.2s
   └─ reasoning_effort: low   → 17 token              → 2.8s
```

加 `reasoning_effort: low` 可把思维链从 245 字符压到 26 字符、token 从 249 降到 17（-93%）。渠道的「参数覆盖」填 `{"reasoning_effort":"low"}` 可全局生效，客户端按需传 `high` 覆盖。

排查时先看返回的 `usage.completion_tokens`：60 左右属正常，200+ 是长思考，与基础设施无关。

## 从 API 管控到资源池 260829

**需求演化**

```text
┌─ ① 四项管控需求 · 起点 ────────────
│    调度切换 / 统一管控 / 密钥申请 / 审计
│    意图：给已有推理栈补上层治理
└────────────────────────────────
            ↓
┌─ ② 疑虑澄清 · 卡点 ───────────────
│   「对外统一了，那用户不能选？」
│    澄清：统一入口 ≠ 统一模型
└────────────────────────────────
            ↓
┌─ ③ 中转站技术调研 · 参照 ──────────
│    倒卖 token 的中转站用什么技术？
│    结论：new-api / one-api 系是事实标准，
│          其「渠道池 + 倍率 + 令牌」可平移自用
└────────────────────────────────
            ↓
┌─ ④ 资源池诉求 · 转向爆点 ──────────
│    要建资源池（NVIDIA 开发者免费额度等）
│    意图改变：治理已有 → 汇聚异构
└────────────────────────────────
```

**① 四项管控需求**：用户原话的四项——付费与本地的调度/切换、API 统一管控、密钥统一申请、审计。此时意图是给已有的推理服务补一层治理。

**② 疑虑澄清**：方案给出后用户追问「new-api 对外是统一的？那用户不能选？」，担心统一入口后失去模型选择权。澄清结论：网关统一的是**入口**（base_url / 鉴权 / 协议三件事），不是模型——用户在请求体里照常带 `model` 字段自选，`GET /v1/models` 返回全部可用模型（本地 + 付费）。"统一"从不等于"只剩一个模型"。

**③ 中转站调研是转向前的参照**：为验证选型是否踩在事实标准上，用户追问中转站（倒卖 API）的技术栈。调研结论：其技术栈高度同质化，核心正是 **new-api / one-api 系**（渠道池 + 倍率 + 令牌分发），外围是发卡网与易支付（交易闭环）、MJ/Suno 等专用协议代理。由此确认两点——一是该体系并非为转售而生，而是通用的**多源资源池化分发**机制，可平移到自用枢纽；二是边界需划清，中转站模式涉及未授权转售与订阅拆分，与自用场景切割（合规提示已写入 README）。这次调研让"资源池"从模糊意图变成可落地的具体形态。

**④ 资源池诉求是转折**：用户随即提出要建立资源池（如英伟达开发者账号的免费额度），需求重心从「治理已有资源」变为「汇聚异构资源」。连锁反应是四项需求权重重排——调度切换跃升为第一需求，"统一管控"的内涵从"管好自己的 vLLM"扩展为"管好本地 GPU + 各路免费额度 + 付费兜底"。

---

**方案**

需求演化的终点是「资源池 + 四项管控」，由此提炼六项关键特性直接对比：


| 关键特性（来源需求）                      | LiteLLM Proxy                                        | new-api                                              |
| ----------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| **异构资源统一接入**（资源池 / 统一管控） | 支持多 provider，但概念是 deployment，偏同模型多副本 | 原生「渠道」概念，异构资源是设计前提                 |
| **多账号池化**（资源池：NVIDIA 多账号）   | 同模型多部署 + 加权 + 冷却                           | 渠道内多 Key 轮询 / 加权随机                         |
| **优先级调度 + 失败切换**（调度切换）     | order 分层 + 冷却 + 五种路由策略                     | 渠道优先级 + 权重 + 自动禁用                         |
| **密钥自助申请**（密钥申请）              | ✖ 管理向，开源版无自助门户                          | ✔ 用户注册后自助建令牌，可限模型 / 额度 / 过期 / IP |
| **用量审计**（审计）                      | spend logs + Prometheus                              | 请求日志 + 额度消耗                                  |
| **限流与配额**（统一管控）                | 虚拟 key + 预算 + 限流                               | 渠道 + 分组 + 限流                                   |

**结论从对比中浮现**：六项中四项两家能力相当，差异仅在精细程度；真正的分野在两项——「密钥自助申请」是**有无之别**（开源版无自助门户，属结构性缺失），「异构资源统一接入」new-api 的「渠道」概念原生面向异构资源池，而 LiteLLM 的 deployment 概念偏同模型多副本。两项均指向 new-api。

**取舍**：LiteLLM 在调度策略上其实更强（延迟 / 成本 / least-busy 感知 + order 分层），但本地只有一条 vLLM、免费额度靠多 Key 轮询，这些策略在本场景用不上——**用不上的强项不构成选型理由**。

**落地位置**

```text
[网关放哪]
  │
  ├─▶ ① 并入 infer/vllm 同 compose
  │     ├─ ✖ 一个目录 = 一个 compose project，切模型的高频 down/up 会误伤网关
  │     ├─ ✖ 裸 compose down 连坐停掉无 profile 的网关
  │     └─ ✖ 用户/令牌/额度是有状态资产，混进可随时重建的推理 project
  │
  └─▶ ② [采纳] 独立 hub/ 目录
        ├─ ✔ 生命周期隔离：网关 7x24，vLLM 随便切
        ├─ ✔ 先例：obs/（监控横切层）已独立成目录
        └─ ✔ 自包含（自带 PG+Redis），dind 重建不影响资产
```

**① 否决并入的决定性理由**：**"一个目录 = 一个 compose project"是硬约束**。vLLM 的 profile 切换是日常高频操作，网关承载有状态资产，两者生命周期频率差一个数量级，同 project 迟早出事。语义归属是第二层理由——网关下游含外部 API 资源，塞进 `infer/`（推理层）名不副实。

**② 独立目录的连带收益**：与 `obs/`（监控横切层）同构，符合"一个模块一个目录一个 README"的规范；自带数据库使网关资产不依赖 dind 内的样例工程。

**命名：语义侧重决定取舍**

用户连问两轮，候选按隐喻分四类——命名之争的本质是"这个模块到底强调什么"：


| 语义侧重                 | 候选                        | 隐喻               |
| ------------------------ | --------------------------- | ------------------ |
| **汇聚**（资源池集中）   | `hub` `pool` `nexus`        | 枢纽 / 水池 / 中枢 |
| **穿过**（流量转发）     | `gateway` `gate` `proxy`    | 闸门 / 管道        |
| **调度**（切换分发）     | `dispatch` `switch` `relay` | 调度台 / 交换机    |
| **并网**（多源统一调度） | `grid` `mesh`               | 电网 / 网格        |

`gateway` 被否：只描述了"流量穿过"，低估了资源池 + 密钥 + 计费 + 审计的完整职责；且将来若加 nginx/caddy 会撞名。`relay` 语义准但国内语境等同于"倒卖中转站"，主动回避。`proxy` 与 `stacks/registry-proxy` 语义冲突。`grid` 类比最精妙（异构资源并网如电网调度火电/风电/光伏），但每次需向人解释——**自解释性优先于隐喻精巧度**，故取 `hub`。

**部署形态**

```text
  客户端 / Open WebUI
        │  令牌 sk-xxx（绑定分组）
        ▼
  ┌──────────────────────────┐
  │    new-api  :18080       │ ← OpenAI 兼容端点 /v1
  └───┬──────────┬───────┬───┘
      │          │       │
      ▼          ▼       ▼
  本地 vLLM   免费额度池   付费 API
  优先级 10   优先级 5    优先级 1
  分组 local  分组 free   分组 local,free

  new-api ──┬──► ① PostgreSQL   用户/渠道/令牌/额度/日志
            └──► ② Redis        令牌缓存/限流计数
```

**① 自带 PostgreSQL，不复用 dind 内的实例**：dind 里的是"样例工程"而非基础设施，dind 重建即丢；网关数据是资产，必须独立数据卷。

**② Redis 用于令牌缓存与限流计数**：可选组件，但加了才能保证多节点/重启场景下的计数一致性。

**版本固定**

用户质疑「为什么是 16-alpine 现在本机不是有 15 么？版本不要用 latest」——前半句被实测推翻，后半句指向了真问题。

```text
┌─ ① 宿主 ────────────────────────
│   ✖ 无 PG / Redis 镜像
│   → 首次部署必须拉取（已配加速源）
└────────────────────────────────

┌─ ② dind ────────────────────────
│   demo-db    → postgres:16-alpine（实测 16.15）
│   pmp-redis  → redis:7-alpine
│   ✖ 全盘无 15 系
└────────────────────────────────
```

**① 宿主无任何 PG/Redis 镜像**：相关镜像全在 dind 隔离环境内，宿主首次部署必须拉取（已配加速源）。

**② 前提错了，问题却是对的**：实测 dind 现役为 16.15、全盘无 15 系，"本机有 15"是记忆偏差——选 16 正是与现役版本对齐，便于排查与离线导入。但"版本不要用 latest"这条成立：`16-alpine` 是浮动 tag（今天 16.15、明天可能 16.16），不符合固定版本要求，遂锁到 `16.15-alpine` / `7.4-alpine`。

new-api 版本同理权衡：最新 `v1.0.0-rc.26` 发布仅 2 天，且 release notes 顶部挂**数据库迁移警告**（额度字段 int32 → 支持 >42 亿，表结构不匹配会启动失败）；rc 版约 7~10 天一版，观察期不足。而该版唯一实质改进（突破 42 亿额度上限）在自用场景根本用不到，**风险收益不成正比** → 取 `v1.0.0-rc.25`。

**上手期的两处易错点**

**镜像名与仓库名不一致**：上游仓库已由 `Calcium-Ion/new-api` 迁至 **`QuantumNous/new-api`**，但 Docker Hub 镜像名仍是 `calciumion/new-api`——按仓库名推镜像名必然落空，查版本时也极易找错仓库，已写入 README 升级须知。

**系统设置入口分散**：`/system-settings/site/system-info` 只展示版本与运行时长，是**只读展示页**，改不了任何东西。真正的设置在 `/console/setting`——站点名称、首页公告（支持 Markdown）、文档地址在「通用设置」标签页，首页背景图 URL 在「其他设置」。Logo/Favicon 官方文档未收录配置项（one-api 时代支持，new-api 文档缺失），自用场景无需折腾；改容器内静态资源会在重建后丢失，得不偿失。
