# VM

## 🚪 Incus 部署 260922

> 从装到租户容器跑通、出网收口、SSH 交付、管理面板

**阶段主线**

```text
[① 影子验证：先不碰 GPU]  ┌ Incus 系统容器落地，租户容器不加卡、无 /dev/nvidia*
                          ├ 租户磁盘走 prjquota 硬配额，看不见宿主
                          └ 宿主 22 容器 / vLLM 全程未中断
                            [顾虑：装前 ACL 是裸的 → 已收口]
        │
        ▼
[② 租户出网收口]          ┌ DOCKER-USER 放行 + 回程 ESTABLISHED
                          ├ ip rule 旁路 mihomo TUN
                          ├ 容器内真实 DNS
                          └ 幂等脚本 + systemd 开机自启
                            [顾虑：不持久化 → 重启后租户能摸宿主服务]
        │
        ▼
[③ 租户 SSH 交付]         ┌ 先用密码登录（暂不上密钥）
                          └ Incus proxy 设备映射容器 22 → 宿主端口
        │
        ▼
[④ 管理面板认证]          ┌ 官方只认客户端证书：装证书 ✖ / 一次性 token ✖
                          └ 网关反代代持证书 → 浏览器免证书
        │
        ▼
[⑤ 入口收敛]              ┌ tailscale → LAN → 内网来源 + 口令
                          └ 专用端口根路径直出，去掉路径前缀匹配
        │
        ▼
[⑥ GPU 交付与门控]        ┌ 热插拔挂卡：容器可热加、VM 不可；4090 无 MIG
                          ├ nvidia.runtime 首次启用需重启容器（实测 2.77s）
                          └ 「宿主优先」只能靠 device add/remove 门控
                            [顾虑：自由显存仅 1.3G，租户能反过来挤爆 vLLM]
```

**① 影子验证：先不碰 GPU**：隔离层用 Incus **系统容器（非特权）**，不直通加速卡；`<Incus 数据目录>` 单独挂在 200G sparse loop 镜像（ext4 + prjquota）→ 租户可做**磁盘硬配额**，绕开宿主"无 LVM / 无 zfs / 内核不支持 btrfs"的现状。租户容器落地即验：无 `/dev/nvidia*`、配额 20G / 2 核 / 4G。

**② 租户出网：三件事缺一不可**：① `DOCKER-USER` 放行 `incusbr0 → 物理网卡` 及回程 `ESTABLISHED`（Docker 默认 `FORWARD DROP` 会掐断）；② `ip rule 5260 / 5261`（租户网段 from/to 走 main 表）旁路 mihomo TUN——否则 **SYN 出得去、SYN-ACK 被 `table 2022` 导进代理**；③ 容器内用真实 DNS，否则拿到 fake-ip `198.18.x`。三条一起固化为**幂等脚本 + systemd 开机自启**。

**③ 租户 SSH 交付**：宿主侧用 **Incus proxy 设备**把容器 `22` 映射到宿主端口（当前 `10.8.0.8:2201`）。登录姿态最后**采纳的是「只有 root 可登录」**（`vm/host/vm-root-only.sh`：锁 `ubuntu` / `tenant` + `PermitRootLogin yes`），而不是早期设想的「普通用户 + 禁 root」——两套姿态互斥，详见文末「脚本清单与部署映射」。

**④ 管理面板：凭证是证书，不是账号密码**

**门面选型（UI）**


| 候选                     | 判定                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------ |
| `incus-ui-canonical`     | ✅ 随 Incus 一起装，**daemon 自己在 `:8443` 提供**，非外挂站点、零额外进程、随包升级 |
| Zabbly Operations Center | ✖ 多机纳管 + OIDC，单机阶段属过度设计                                               |
| 自研面板                 | ✖ 到 GPU 门控与租户自助那层才有必要                                                 |

**登录路径**

```text
[面板登录]
  │
  ├─▶ [A] 浏览器直连 :8443 手动装客户端证书
  │     → ✖ 每台机器都要把 p12 塞进系统证书库（macOS 强制要密码）；换机器 / 换浏览器即重来
  ├─▶ [B] 一次性 token 换证书（UI 的 certificate-add 页）
  │     → ✖ token 生命周期绑在生成进程上：「trust add」阻塞等待交换，
  │        进程被回收 → 服务端 pending operation 一并消失 →
  │        报 No matching certificate add operation found
  └─▶ [采纳 C] 网关反代代持客户端证书（tls_client_auth 向上游出示自己）
        浏览器只过一道普通口令，面板侧认证在 反代↔daemon 之间完成
```

**A**：Incus 7.0 已移除 `core.trust_password`，**官方路径是证书而非账号密码**——UI 没有用户名 / 密码登录，凭证就是客户端证书本身。

**B**：token 不能"复制下来慢慢试"——它只在生成命令存活期间有效，命令一退出即作废，「先生成、待会再用」这个用法本身不成立。

**C**：浏览器侧不再需要任何证书或 token，**面板因此不存在"Incus 登录页"**，过网关口令后直接进管理界面。

**⑥ GPU 交付：容器能热加、VM 不能，且卡没有中间档**

挂载能力的实测结论：`gputype=physical` **仅容器支持热插拔**（VM 必须重启）；`mig` **不支持热插拔**，而且 **RTX 4090 是消费卡、`MIG Mode` 直接是 `N/A`**；`vGPU` 字段不存在。所以**卡是不可切分的原子单位**——「只给 8G 显存」这种粒度不存在。`nvidia.runtime`（用于注入主机 `libcuda`）官方标注 **Live update: no**，**首次启用必须重启容器**。

**GPU 挂载实测**（宿主服务零中断）


| 动作                                                                | 是否需重启     | 对宿主 vLLM 的影响                     |
| ------------------------------------------------------------------- | -------------- | -------------------------------------- |
| `incus config device add <实例> gpu gpu gputype=physical pci=<BDF>` | 否（热插拔）   | 无：不重载驱动、不夺独占锁、不分配显存 |
| `incus config device remove <实例> gpu0`                            | 否             | 无                                     |
| `incus config set <实例> nvidia.runtime=true`                       | **是（容器）** | 无（只重启容器，驱动不重载）           |

挂载 / 摘除 / 重启容器全程，宿主侧逐项比对**完全一致**：vLLM `/health` `200`、`22726 / 22724 MiB`、`util 100%`、`TP0 19502 / TP1 19500`、`peakminer 3196 × 2`、docker `22` 容器。容器重启耗时 **2.77s**，IP 不变。

**PID 隔离挡住了进程可见性**：租户侧 `nvidia-smi` 的 Processes 段恒为 `No running processes found`，`ps` 只看得到自己的 19 个进程——**租户能算出宿主把卡占满了，但定位不到是哪个进程**。

**能不能限制租户的 GPU 占用？**


| 机制                         | 可用性 | 说明                                                                       |
| ---------------------------- | ------ | -------------------------------------------------------------------------- |
| MIG 切分                     | ✖     | `MIG Mode: N/A`，消费卡驱动不解锁                                          |
| vGPU / SR-IOV                | ✖     | GeForce 不支持                                                             |
| 显存 cgroup 配额             | ✖     | NVIDIA 未提供 VRAM 限额                                                    |
| MPS                          | △     | 能限并发份额与 pinned memory，**不能限总显存**；且客户端不设环境变量即绕过 |
| 按卡分配（1 张 / 2 张）      | ✅     | 唯一由硬件粒度保证的限制                                                   |
| **门控 device add / remove** | ✅     | **推荐**：默认不挂卡，宿主空档才给；秒级生效、零重启                       |
| 熔断看门狗                   | ✅     | 宿主可按`/proc/<pid>/cgroup`（`lxc.payload.*`）认领租户进程并摘卡          |

**仅 CPU / 内存 / 磁盘能硬限**（`limits.cpu=2`、`limits.memory=4GiB`、prjquota 20G）；**GPU 是"要么全给、要么不给"**。

**坑：出网侧**

1. **装前 ACL 是裸的**：容器一起来就能打开宿主 Portainer（`9443 → 200`）→ 用 `DOCKER-USER` + `INPUT` 双层收口（不动 Docker / tailscale 自有链）。
2. **回程被 mihomo 吞**：SYN 出得去、SYN-ACK 也回来了，但被 `table 2022` 导进 TUN → 靠 `ip rule 5260 / 5261` 旁路 + 回程 `ESTABLISHED` 放行。
3. **DNS 拿到假地址**：容器沿用宿主链路会拿到 fake-ip `198.18.x` → 容器内改用真实 DNS。
4. **规则不持久化即安全事故**：重启后 ACL 失效 = 租户能直接摸宿主服务 → 固化成幂等脚本 + systemd 开机自启。

**坑：面板侧**

1. **非白名单来源静默落到兜底导航页并返回 200**：现象是"页面开了但不是面板"、无任何报错，压力全压在现象侧 → 面板路径对非白名单来源改为**明确 404**。
2. **UI 静态资源只发 `Last-Modified`、无 `Cache-Control`**：浏览器复用旧入口壳，资源被拦时报 `Failed to fetch dynamically imported module`，看起来像"页面半开" → 反代统一 `Cache-Control: no-store` 并去掉 `Last-Modified` / `Etag`。
3. **白名单不能整体写 `172.16.0.0/12`**：Docker 网段 `172.17~172.23` 落在其中，会连带放行全部容器（含 privileged 的 dind）→ 用 `not remote_ip` 显式排除这些 /16。
4. **站点地址写死 `<IP>:1001` 时 Host 不匹配会返回 200 空响应**：容器用 docker0 网关 IP 访问时不命中任何站点，Caddy 返回空响应、日志记为 `NOP`——状态模糊且看不出这是拒绝 → 改为 `http://:1001` 端口级匹配，全部交给准入门裁决。

**坑：GPU 侧**

1. **自由显存只剩 1.3G**：`22726 / 24564`、`22724 / 24564` → 租户一旦拿到卡，**随时能把 vLLM 挤爆**。所以「挂卡」这个动作本身就是把门控绕过，**验证完必须摘**。
2. **`nvidia.runtime` 不是热更新**：只加设备的容器**有 `/dev/nvidia*` 却没有 `libcuda` / `nvidia-smi`**，表现为"挂了卡却用不了" → 必须补 `nvidia.runtime=true` 并**重启容器**才注入用户态库。
3. **别用 `/proc/driver/nvidia/*` 判定**：proc 条目不隔离，租户**没挂卡也能读到**型号 / GPU UUID / 驱动版本，是**假阳性**；真判据只有 `/dev/nvidia*` + `nvidia-smi -L`（或 `cuInit`）。
4. **`nvidia-smi -L` 会带出 GPU UUID**：对外输出必须 `sed 's/ (UUID: [^)]*)//'` 剥掉，否则是硬件指纹。
5. **Persistence-M 为 `Off`**：`nvidia-smi` 显示 `Persistence-M: Off`，进程全部退出后驱动会卸载，**下一次用卡有初始化等待** → 高并发场景要考虑。

**坑：交付面**

1. **脚本注释就是泄露源**：`gpu-check` 早期版本在文件头写了 `incus file push … tenant01/…` 和「不会影响宿主正在运行的 **vLLM**」——**租户 `cat /usr/local/bin/gpu-check` 就能看到**。同类自曝还有：运行期输出里的「不影响**宿主服务**」、第 6 节「看不到宿主的 vLLM进程」、以及 FAIL 提示里的 `incus config device add` 宿主命令。**结论：任何进入租户环境的文件，按"注释也会被读"的标准审查；这直接催生了 `vm/host/` 与 `vm/tenant/` 的目录分界。**
2. **宿主进程名其实没泄漏**：实测租户侧 `nvidia-smi --query-compute-apps` 为空、`ps` 仅 19 个自身进程、`/proc/1/cgroup` 为 `0::/init.scope`、`dmesg` 被拒——**泄露是脚本自己说出去的，不是系统漏的**。
3. **脚本之外仍有硬件侧信道**（租户可读，目前无掩盖手段）。


| 泄露项                    | 实测值                                           |
| ------------------------- | ------------------------------------------------ |
| 主板 / BIOS               | `HUANANZHI H12D-8D` / `1.8`                      |
| CPU                       | `AMD EPYC 7302 16-Core`                          |
| PCI 设备数                | **92 个**（宿主拓扑）                            |
| 宿主物理内存              | `/proc/mounts` 里 `size=65778964k` ≈ 64G        |
| GPU UUID / VBIOS / Bus Id | `GPU-4add8f03-…` / `95.02.3C.00.EC` / `81:00.0` |

已挡住：`/proc/meminfo` 报的是容器限额 4G、`dmesg` = `Operation not permitted`、`/etc/hostname` 仅 `tenant01`、文件系统内无任何业务关键字。**GPU 指纹只要挂卡就必然暴露**，没有掩盖手段。

**脚本清单与部署映射**（260922 收口后）

目录按「运行位置」分两层——**目录本身就是交付边界**：`vm/host/` 只跑在宿主，`vm/tenant/` 是要推进租户的交付物。


| 源文件                        | 部署位置                              | 谁执行                                                        |
| ----------------------------- | ------------------------------------- | ------------------------------------------------------------- |
| `vm/host/tenant-ctl.sh`       | 不部署（宿主直接跑）                  | 人工，统一管理入口                                            |
| `vm/host/incus-tenant-net.sh` | `/usr/local/sbin/incus-tenant-net.sh` | `incus-tenant-net.service`（开机自启）+ `tenant-ctl.sh apply` |
| `vm/host/vm-root-only.sh`     | 不部署                                | 人工：`vm-root-only.sh <实例> [root口令]`                     |
| `vm/tenant/gpu-check.sh`      | 租户内`/usr/local/bin/gpu-check`      | 租户 SSH 后执行`gpu-check`                                    |
| `vm/tenant/ssh-setup.sh`      | 租户内就地执行                        | 人工                                                          |

```bash
# 宿主侧：网络收口规则（systemd 拉起的那份）
install -m 0755 vm/host/incus-tenant-net.sh /usr/local/sbin/incus-tenant-net.sh

# 租户内：对外自检脚本
incus file push vm/tenant/gpu-check.sh <实例>/usr/local/bin/gpu-check --mode 0755

# 租户内：SSH 配置（就地执行）
incus exec <实例> -- bash -s < vm/tenant/ssh-setup.sh
```

⚠️ **两套登录姿态互斥，先定一套**：`vm-root-only.sh` 是「只有 root 可登录」；`vm/tenant/ssh-setup.sh` 是「开普通账号 + 禁 root 登录」。当前实例实际处于**前者**（`passwd -S root` = `P`、`tenant` = `L`、`PermitRootLogin yes`、无 `/etc/sudoers.d/tenant`）——与 ③ 节写的「禁 root 登录」相反，**以 `vm-root-only.sh` 为准**。

⚠️ **顺序陷阱**：`ssh-setup.sh` 会把 `PermitRootLogin` 改成 `no`。若此时普通账号是锁定态（当前 `tenant` = `L`），改完 **`2201` 上谁都登不进去**，只剩 `incus exec` 兜底。必须先给普通账号设好口令，再改 `PermitRootLogin`。

**`tenant-ctl.sh` 命令清单**（宿主侧统一入口）

```text
tenant-ctl.sh list                        租户总览（状态/IP/配额/磁盘）
tenant-ctl.sh status  <t>                 资源使用详情 + GPU + 入口
tenant-ctl.sh gpu     <t> status          查看已挂 GPU（含租户侧 nvidia-smi -L）
tenant-ctl.sh gpu     <t> on  [卡序号...] 挂 GPU（不带序号=全部）
tenant-ctl.sh gpu     <t> off             摘掉全部 GPU（连带 unset nvidia.runtime）
tenant-ctl.sh net     <t>                 网络收口自检（ACL/出网/DNS）
tenant-ctl.sh apply   [t]                 幂等施加网络规则（内部调 incus-tenant-net.sh）
tenant-ctl.sh start|stop|restart|shell|ssh|quota|destroy
```

要点：`gpu on` **按 PCI 匹配而非按设备名**，所以重复执行幂等、不会把同一张卡挂两遍；首次会自动设 `nvidia.runtime=true` 并重启容器（后续增删卡**零重启**）；`apply` 只是**编排**独立脚本，systemd 自启不受 CLI 改动影响。

**交付口径**（给租户的解释，不涉任何宿主内部信息）

- 主口径：**「这台 GPU 已纳入平台算力共享池，当前满载服务中；平台任务优先于租户，只在空档期释放。」**
- 三句配套：问负载类型 → 「平台侧资源组成不属于交付范围」；问何时释放 → 「由平台统一调度，不承诺具体时长」；问能否让一让 → 「平台任务优先级高于租户，交付前已明确」。
- **不用「在跑训练任务」**：训练总会结束，届时无法解释 `100%` 仍在；「算力共享池」没有期限概念，可长期沿用同一口径。

## ⚖️ 多租户强隔离方案 260921

> 把宿主机切一部分算力（CPU / 内存 / 磁盘 / GPU）分给**外部人员**训练，现有业务（vLLM 推理、算力共享、监控、docker 栈）不受扰动，租户**看不见也摸不到**宿主与其他租户。

```text
[业务画面]
  宿主现有业务（保持原样，不动）
  ├─ vLLM 推理（双卡 TP=2）· 算力共享· docker 栈（portainer / gitea / 监控 / hub…）
  │
  ▼  切一块出来
  [租户池]  外部人员，一人一间"隔离房"
  ├─ 看得见的：自己的 SSH / 自己的环境 / 自己的配额 / 自己发布的服务
  ├─ 看不见的：宿主服务、宿主数据、其他租户
  └─ GPU：只用宿主闲置的空档，宿主一用就收走（宿主优先）
```

**三条硬约束**


| 约束             | 结果                           |
| ---------------- | ------------------------------ |
| 租户需要可信验证 | 任何"能摸到宿主"的通道都要阻断 |
| GPU 没有空闲     | 只能共卡 + 空档时分，不能整卡  |
| 不加新硬件       | 资源只能切分 + 配额，不能扩容  |

1. **整卡直通（KVM / Kata / vfio）**：隔离最彻底，但直通就要宿主交出这张卡 → 与「共享卡 + 宿主优先」硬冲突
2. **沿用 dind（privileged 容器）**：实测可直连宿主 `
3. **NVIDIA 给显存配额**：不存在（无 cgroup 显存限额）→ 「宿主优先」只能靠门控互斥，不能靠配额
4. **以为配个代理出口就行**：宿主连 `223.5.5.5` 都走 Mihomo TUN、DNS 是 fake-ip `198.18.0.2` → 租户必须策略路由旁路 + 独立 DNS，否则等于还在走代理或拿到假地址
5. **只选隔离层**：多租户真正难的是 GPU 让出机制、统一入口与跳板机、模板与一键删除

**方案框架**

```text
① 隔离层  租户以什么形态跑          候选：Incus 系统容器（非特权，首选）/ 单应用容器（更轻更弱）
② 资源层  配额 + GPU 让出机制       候选：门控脚本（宿主空闲给卡、需要收卡，可加队列与超时）+ cgroup 硬配额
③ 门面层  统一 Web 管理 + 跳板机    候选：JumpServer（Web+堡垒+审计一体，首选）/ Warpgate（轻量）
④ 运维层  模板 / 脚本 / 台账 / 看板  复用：Incus profile、Grafana + Prometheus（已有）
```

可组合方案包


| 隔离层            | 资源 / GPU    | 门面                          | 判断                 |
| ----------------- | ------------- | ----------------------------- | -------------------- |
| Incus 系统容器    | 门控 + 硬配额 | JumpServer + Caddy（已有）    | 满足全部硬门槛       |
| 单应用容器 + 加固 | 门控 + cgroup | Warpgate + Caddy + 自建小面板 | 租户少、省资源       |
| KVM 整卡直通      | 分时切换      | JumpServer                    | 与硬约束冲突，需取舍 |
| dind 加固         | 现有          | 现有 Portainer                | 隔离不达标，仅过渡   |

**实测锚点**（后来者重做不用再测）


| 事实            | 值                                                                         | 用在哪                     |
| --------------- | -------------------------------------------------------------------------- | -------------------------- |
| GPU 双卡满载    | vLLM TP=2 各 19.5G + peak 各 3.2G，util 100%                              | 决定只能共卡               |
| 宿主端口暴露面  | `9090 / 3000 / 9443 / 18080 / 5000 / 6000 / 3100 / 2222` 等 `0.0.0.0` 监听 | 决定必须收口 + ACL         |
| mihomo 接管程度 | `223.5.5.5 → dev Mihomo`；DNS 是 fake-ip `198.18.0.2`                     | 决定旁路 + 独立 DNS        |
| ephemeral 区间  | `32768-60999`                                                              | 决定租户端口池不能落进去   |
| IOMMU 分组      | group16`c4:00.0/.1`、group31 `81:00.0/.1`（同组是否混入其他设备 **未验**） | 若日后转向整卡直通可直接用 |
| 根文件系统      | ext4、无 LVM、无 zfs、内核不支持 btrfs                                     | 决定磁盘配额要额外成本     |
| 主板            | ASPEED BMC（大概率带 IPMI）                                                | 强隔离的盲区，先查         |
