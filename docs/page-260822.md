# 外部算力占用对推理性能影响的评测报告

> 2026-08-22 · Qwen3.8-27B (AWQ, W4A16) · vLLM 0.26 · 2 × RTX 4090

## 评测概述

**评测目的**：量化外部算力占用对 vLLM 推理服务的性能影响，为 GPU 资源调度决策提供依据。

**评测环境**：


| 项目     | 配置                                         |
| -------- | -------------------------------------------- |
| 模型     | Qwen3.8-27B (AWQ, W4A16)                     |
| 推理引擎 | vLLM 0.26，tensor-parallel=2，max-num-seqs=4 |
| 硬件     | 2 × RTX 4090 (24GB)                         |
| 评测时间 | 2026-08-22                                   |

## 评测方法

**测试用例**：固定 3 道短题（数学计算 / 代码生成 / 文本总结），输入仅数十 token，输出上限各 128 tokens，保证跨轮次可比。

**指标定义**：


| 指标     | 定义                             | 反映能力       |
| -------- | -------------------------------- | -------------- |
| TTFT     | 发出请求到收到首个 token 的时间  | 响应速度       |
| 输出吞吐 | 输出 token 数 ÷ 总耗时（tok/s） | 单请求生成效率 |

**控制变量**：同一脚本、同一组用例，仅切换占用状态（运行 / 停止）各测一轮。

**并发与上下文设定**（重要边界）：


| 变量       | 本次取值      | 说明                                                                |
| ---------- | ------------- | ------------------------------------------------------------------- |
| 并发       | **1（串行）** | 脚本逐条发请求，一条完成才发下一条；服务端`max-num-seqs=4` 从未触发 |
| 输入上下文 | 数十 token    | 远低于`max-model-len=32K` 上限，KV cache 占用极小                   |
| 输出长度   | 128 tokens    | 固定上限，跨轮次可比                                                |

因此本次测得的是**短上下文 × 单请求路径**的基线：不涉及并发排队、长注意力与显存压力，结果聚焦于"纯算力竞争"本身（见理论分析）。若并发或上下文变化，数值会不同，见"评测边界"。

## 评测结果


| 指标                | 占用运行中 | 占用停止 | 变化   |
| ------------------- | ---------- | -------- | ------ |
| 输出吞吐（tok/s）   | 19.5       | 75.3     | ↓ 74% |
| 首字延迟 TTFT（ms） | 155        | 124      | +25%   |

```
输出吞吐 (tok/s)            越宽越快
占用中  ████████ 19.5
空闲    ████████████████████████████████ 75.3

首字延迟 TTFT (ms)          越短越快
占用中  ████████████ 155ms
空闲    ██████████ 124ms
```

## 数据分析

将总耗时拆解到单步粒度，定位差距根源：


| 粒度                  | 占用中   | 空闲     | 差异   |
| --------------------- | -------- | -------- | ------ |
| 128 token 总耗时      | 6.5 s    | 1.6 s    | —     |
| **单 token 平均耗时** | ≈ 51 ms | ≈ 13 ms | 3.9 倍 |

- 吞吐骤降 74% 的根源在**单步生成耗时被拉长 3.9 倍**，经串行解码逐次累积
- TTFT 仅 +25%（+31ms），与单步差距（约 38ms）同量级，符合"只承担一次差距"的预期

## 理论分析

### 第一层：争的是算力，不是显存

外部程序占用 1.4GB 显存，vLLM 占用 21GB，合计 22.5GB，未触及 24GB 上限——**显存层面没有竞争**。真正被争抢的是**计算单元（SM）**：算力密集型程序长期占满 SM，vLLM 的计算内核只能挤在调度缝隙里穿插执行。

```
GPU0 时间线（单帧内）
外部占用  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  长期占满 SM
vLLM      ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓   ▓▓▓         挤缝隙执行，每步被拉长
```

### 第二层：单步如何被拖慢

解码每生成一个 token，需一次完整的矩阵前向（含逐层 matmul）。SM 被抢占时，内核排队等待调度，等效单步耗时从 13ms 拉到 51ms。AWQ 量化的 W4A16 模型本身计算量低，**对调度等待更敏感**——空闲时更快，被抢占时等待占比更大。

### 第三层：结构因素如何放大差距

两个结构因素把"单步慢 3.9 倍"放大成"整体慢 3.9 倍"：

1. **双卡同步（tensor-parallel=2）**：每步生成要求两卡同步汇合（all-reduce），慢卡决定整步耗时。

```
GPU0  [半个模型] + [外部占用] → 每步都慢  ← 瓶颈
           │ 同步等待（每步必等）
GPU1  [半个模型]（完全空闲） → 每步空等，无法补偿
```

2. **解码串行性**：128 个输出 token 逐字生成，前一步是后一步的前置。单步 13→51ms，串行 128 步后即 1.6s→6.5s。

```
prefill（不受影响）：一次并行前向算完整段输入 → 出第一个字（只被"等"一次）
decode（被放大）：tok1 → tok2 → ... → tok128（每一步都被拖慢）
```

### 第四层：为什么 TTFT 几乎不受影响

TTFT = 排队 + 预填充 + 首字解码，三个环节均不敏感：

1. 评测为单请求串行，**无排队**（max-num-seqs=4 未触发）
2. 预填充是**一次并行前向**，输入仅几十 token，被抢占只影响一次，毫秒级
3. 首字只承担**一步**解码差距（约 38ms），实测 +31ms 与之吻合

对比之下，吞吐承担 128 步 × 每步 38ms，差两个数量级——这就是"首字几乎不变、吞吐暴跌"的根源。

### vLLM 配置对评测结果的影响

评测结果并非配置无关，以下配置直接或间接参与了本次现象：


| 配置项                 | 当前值    | 对本次评测的影响                                                                                                                   |
| ---------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| tensor-parallel        | 2         | **放大因素**：单卡被占拖累整步，若单卡部署则无空等，但绝对吞吐也约减半                                                           |
| max-num-seqs           | 4         | **未生效**：本次并发=1，从未并行处理多个序列；该参数约束的是并发场景（见"评测边界"）                                               |
| max-model-len          | 32768     | **上限未触及**：输入仅数十 token，KV cache 占用极小；但上下文长度本身是敏感变量，长上下文会因注意力计算量增长而抬高单步耗时与 TTFT |
| gpu-memory-utilization | 0.90      | 无影响：短输入下 KV cache 占用小，显存未碰线（22.5 < 24GB），竞争在算力而非显存                                                    |
| enable-prefix-caching  | 开        | 无影响：用例彼此独立，无公共前缀可复用                                                                                             |
| 量化格式               | AWQ W4A16 | 间接影响：单步计算轻，但调度等待占比大，对抢占更敏感                                                                               |

**一句话**：本次评测用"并发=1 + 短输入"隔离了并发、缓存与显存压力，结果主要反映**算力竞争 × TP 同步放大**两个因素；若改并发或上下文，具体数值会变，但"共享算力必拖慢生成"的方向不变。

## 评测边界

本次结论仅适用于**短上下文、单请求串行**场景，以下场景未覆盖、不可外推：


| 未覆盖场景                          | 预期影响                                                                                                         |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 并发请求（如 WebUI 多用户同时提问） | `max-num-seqs` 开始生效，总吞吐通常上升但单请求延迟恶化；算力占用下并发排队效应更强，吞吐差距可能进一步拉大      |
| 长上下文（≥4K tokens）             | 每步注意力计算随 KV 长度线性增长，单步耗时、TTFT、显存占用均上升，tok/s 下降；与算力占用叠加后趋势不变但幅度改变 |
| 多模型 / 大批量混跑                 | 调度竞争更复杂，占用程序的影响路径可能不同                                                                       |

如需在这些场景下做决策，应补充对应条件的评测，方法与脚本不变。

## 结论

1. 外部算力占用对**输出吞吐**影响显著（↓ 74%），对**首字延迟**影响有限（+25%）
2. 差距根源在单步生成耗时被拉长 3.9 倍，经双卡同步与串行解码两级放大
3. 决策启示：生成密集型场景应避免与算力任务共享 GPU；首字响应敏感场景受影响较小；改用单卡部署可消除空等但需接受吞吐减半
4. **适用边界**：上述结论基于短上下文（数十 token）与单请求串行（并发=1）；并发或长上下文场景需按"评测边界"补测
