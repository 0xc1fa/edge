# MTP 解码优化评测报告

> 2026-08-23 · Qwen3.8-27B (AWQ, W4A16) · 2 × RTX 4090 · 后台算力任务满载共存 · 测试脚本 `/root/edge/benchmark/`

## 一、评测概述

**目的**：量化 vLLM 升级 + MTP 解码的实际收益，调研"MTP 未发挥"的根因并测试优化，给出**在当前部署环境（后台算力满载共存）下的最佳配置**。

**环境**：


| 项目 | 配置                                                                        |
| ---- | --------------------------------------------------------------------------- |
| 模型 | Qwen3.8-27B (AWQ, W4A16)，官方自带 MTP 头                                   |
| 引擎 | v0.26.0（基线）→ v0.27.1（MTP 支持，v0.27.1 起支持 Qwen3.8 MTP）           |
| 硬件 | 2 × RTX 4090 (24GB)，GPU 99% 满载（后台算力任务共存，与生产一致）          |
| 配置 | TP=2 · kv-cache-dtype=fp8 · gpu-memory-utilization=0.90 · max-num-seqs=4 |

**实验矩阵**（同引擎 v0.27.1 仅开关 MTP，排除版本/参数干扰）：


| 实验   | MTP | max-num-batched-tokens | 场景         |
| ------ | --- | ---------------------- | ------------ |
| 基线 A | 无  | 4096（升级前默认）     | 串行         |
| 对照 B | 无  | 12288（调优）          | 串行 / 并发4 |
| 优化 C | n=2 | 12288                  | 串行 / 并发4 |
| 优化 D | n=1 | 12288                  | 并发4        |

## 二、评测结果

### 2.1 串行单请求（3 用例，max_tokens=256，稳态取 2 轮均值）


| 配置                     | tok/s | TTFT(ms) | 备注                     |
| ------------------------ | ----- | -------- | ------------------------ |
| v0.26.0（升级前默认）    | 24.1  | 399      | 历史基线                 |
| v0.27.1 无 MTP（对照 B） | 24.1  | 179      | 引擎升级本身无性能差     |
| v0.27.1 + MTP n=2（C）   | 25.0  | 186      | **tok/s +4%**，TTFT 持平 |

**关键发现**：串行场景下 TTFT 从 399→179ms（**-55%**）主要来自 `max-num-batched-tokens 4096→12288` 调优（prefill 批处理能力 ×3），**与 MTP 无关**。MTP 的净收益为 tok/s +4%。

### 2.2 并发 4 请求（同用例 ×4，聚合吞吐）


| 配置                   | 聚合吞吐(tok/s) | 相对无 MTP | 平均 TTFT   |
| ---------------------- | --------------- | ---------- | ----------- |
| v0.27.1 无 MTP（B）    | 61.5 / 63.1     | —         | 545-1190ms  |
| v0.27.1 + MTP n=2（C） | 43.1 / 36.8     | **-40%**   | 1190-4698ms |
| v0.27.1 + MTP n=1（D） | 45.2            | **-27%**   | 4157ms      |

**反直觉发现**：并发下 MTP 反而大幅拖慢吞吐（-27%~-40%），调低推测步数只能止损不能转正。

### 2.3 MTP 机制验证（metrics 实测）


| 指标         | 串行  | 并发4 |
| ------------ | ----- | ----- |
| 接受率       | 77.1% | 87.3% |
| 位置0 接受率 | 83.8% | —    |
| 位置1 接受率 | 70.4% | —    |

MTP 机制完全正常（接受率 77-87%），问题不在正确性而在**算力开销**。

## 三、调研：为什么 MTP 未发挥 + 官方文档佐证

**根因链**（实验 + 源码 + 官方文档三线印证）：

1. **推测解码的本质**：每次解码步 = [草稿前向 + 主模型验证前向]，计算量约为原来的 n+1 倍，换取串行 step 数减少
2. **适用前提**：vLLM 官方文档明确——推测解码针对**"低至中等 QPS 的*内存受限*（memory-bound）工作负载"降低 token 间延迟**；"如果并发场景已经是计算/带宽瓶颈，推测解码的收益会显著下降"
3. **当前环境是计算受限**：后台算力任务把 GPU 打到 99% 满载，草稿生成需要与其他 GPU 计算任务抢占 SM。空闲时草稿算力"免费"，满载时草稿算力"昂贵"——单请求尚能小幅正收益，并发时推测开销直接反噬

```
              串行（低负载）              并发4（计算受限）
无MTP   ████████████████ 24.1   ████████████████████████████████████ 61.5
MTP n=2 █████████████████ 25.0   ████████████████████ 36.8  ← -40%
```

4. **官方建议调参无效**：官方建议高并发下调低 `num_speculative_tokens` 止损（实测 n=1 从 -40% 收窄到 -27%），但无法转正——环境本质是计算受限，非参数问题

## 四、显著提升路径（实测，与 MTP 无关）


| 优化                             | 效果                 | 实测数据                      |
| -------------------------------- | -------------------- | ----------------------------- |
| **并发 batch 利用**              | 聚合吞吐**+155%**    | 串行 24.1 → 并发4 61.5 tok/s |
| **max-num-batched-tokens 12288** | TTFT**-55%**         | 399 → 179 ms（串行）         |
| 引擎升级 0.27.1                  | 无性能差，仅能力提升 | 24.1 vs 24.1 tok/s            |

## 五、结论与推荐

1. **MTP 在当前环境（后台满载 + 并发）是负优化**（-27%~-40%），根因是计算受限场景不适用推测解码（官方文档佐证）。**推荐默认关闭**
2. MTP 仅在**延迟敏感、低并发（≤2）、GPU 有余量**的场景有正收益（单请求 +4% tok/s）；若后台任务停止（GPU 空闲），历史参考可回到 +39%
3. **显著提升来自并发 batch（+155%）与批处理调优（TTFT -55%）**，而非 MTP
4. **配置交付**（`/root/edge/infer/vllm/docker-compose.yml` 已按此拆分）：
   - `docker compose --profile qwen38 up -d` → **默认推荐**（v0.27.1 无 MTP，吞吐优先）
   - `docker compose --profile qwen38-mtp up -d` → 延迟敏感低并发场景（MTP n=2）
   - 两个 profile 同引擎 v0.27.1，仅推测开关不同，可随时对照
